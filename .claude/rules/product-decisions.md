# プロダクト判断の記録

自動メモリの代わりに使う、共有の記憶。新しい判断が出たら、ここに1行で追記してコミットする。
元資料は owner の Obsidian ノート（`4_Project/built-with-claude-japan-2026/CONTEXT.md`）。

## 確定した判断

- D-01: ゲームを作るのではなく、インディー開発者の「作れるのに発信できない」を解く。
- D-02: 録画後の編集はやらない。mp4 を Claude に渡せば済むので差別化にならない。勝負するのは録画の前（何を、どの画角で、何秒撮るか）。
- D-03: 対象は個人インディー開発者。owner 自身が当事者であることを説明の根拠にする。
- D-04: ソロ参加。縦スライス1本に絞る。
- D-05: 既存の Henshusha の設計は流用しない（用語の参照はしてよい）。
- D-06 / D-07 / D-07b: エンジン密接型で、第一対象は UE5（Sequencer Python + Movie Render Queue）。提出物は UE5 のみ。
- D-09: UE5 の CLI 駆動はリスクではない（`UnrealEditor-Cmd` + PythonScript commandlet は実測済み）。
- D-11: エンジン展開の順は UE5 → Unity → Godot → Roblox。UE5 で納得できる画が出るまで、次のエンジンには手を付けない。
- D-12: 成果物はティザー1本（30〜60秒）。短尺は次回以降。
- D-13: 部分修正ループを設計の芯に置く（ショット単位の再レンダ、定義と出力の分離、状態の保持、安いプレビュー）。
- D-14: 差別化は3層で置く。①修正ループを製品の中心に置く ②ティザーの型 `hook → establish → escalate → title` を同梱する ③1ビートに3バリアントを出す。汎用の Unreal エージェントとは正面から戦わない。
- D-15: open-design（nexu-io/open-design）型のローカル daemon と Web UI（`shotpilot serve`）を、標準ライブラリだけで薄く載せる。正本は shots.yaml のまま、リクエストごとに Workspace を開き直す。Next.js / Electron / SQLite は持ち込まない。狙いはデモの「1枚だけ rendered、残りは reused」を画面で見せること。（D-16 でブラウザ表示をやめ、アプリのウィンドウに置き換えた）
- D-16: 全体を Rust に書き換え、Tauri のデスクトップアプリ（`shotpilot-app`）にする。ブラウザで開く Web UI はやめる。Python は UE の中で動く `sp_entry.py` だけに留める。fingerprint は Python 版と同じバイト列を hash するので、それまでに UE で撮った take はそのまま再利用できる。
- D-17: アプリの画面は open-design のスタジオ画面（左に会話、右にキャンバス）に倣い、キャンバスの下に動画エディタのタイムラインを置く。直し方は自然言語が主で、人間は「どのショットの、どのフレームの、どこか」をタイムラインとプレビューの範囲選択で指す。Claude にはそのフレーム画像と範囲を渡し、編集範囲はコードで選んだショットに限る。数値の直接編集（調整）は従に置く。
- D-18: Claude への接続は、既定でユーザーの Claude Code を headless（`claude -p`、stream-json）で呼ぶ。Agent SDK が内部でやっていることと同じで、Node や Python を持ち込まずにログイン済みのアカウントで動く。API キーはアプリ内で入力でき、設定フォルダに保存して画面には返さない。ACP（Zed の Agent Client Protocol）は複数エージェントに対応するときに検討する。
- D-19: BGM と SE を扱う。正本は shots.yaml（BGM は `audio:`、SE は各ショットの `sfx:`）で、cut のときにミックスして載せる。音は fingerprint に入れないので、直しても撮り直しは起きない（D-02 の「録画後の編集はやらない」の例外として、定義の一部として扱う）。編集はタイムラインのレーン（ドラッグ、数値）と、Claude への「音だけ」の指示。検証は earshot（MIT）の critique のうち、ML モデルを使わない部分を Rust に移植したサウンドチェックで、プロのローンチ映像7本と比べる。

- D-20: 品質と再現性は open-design 式で上げる。強いモデルに頼らず、①主張の強いリファレンス（数値の規則、実在トレーラーの「Inspired by」様式、骨格テンプレート）を決め打ちで渡し、②コードのショット検査（`shotcheck.rs`）で差し戻す。「Haiku でも撮れる」を評価ハーネスの数字で示す。
- D-21: アプリは業界の工程に合わせ、「ブリーフ → 構成 → 構図 → 撮影 → 仕上げ」の工程バーにする。ブリーフは `shots.yaml` の `brief:`（編集的、撮り直しなし）。構図の承認は画の指紋に紐づけ、画が変わると外れる。P0 は承認を止め、推定の閾値は P2 に留めて実測（ffmpeg のシーン検出）で校正する。2〜3案からの選択と評価ハーネスは次の段。

- D-22: Claude には自己検証をさせない（open-design の OD Next に倣う）。プロンプトに検証・チェックリスト・自己採点の指示を書かず、セオリーはブリーフ・骨格・数値の規則として生成前に渡して1回で組ませる。ビート順や尺の範囲はコードで整える。shotcheck はコードの検査として画面に出すだけで、自動の差し戻しはしない。直すかどうかは人間が決める（「Claude に直させる」）。検証するのは人間で、安い段階（previz / still）の承認がその場になる。
- D-23: ブリーフにムードボードを置く。手持ち画像か OpenAI の画像生成（Claude は画像を生成できないため）で色・光・空気感を先に合意し、plan のときに Claude へ画像として見せる。生成画像は雰囲気の参照だけに使い、ティザーの画はすべてゲームから撮る。ショットごとの絵コンテ生成は後回し。生成は既定でログイン済みの Codex CLI を呼ぶ（D-18 の Claude Code と同じ考え方で、キー不要）。API キー（`gpt-image-2`）は代替。
- D-24: ブリーフの前に工程0「ロケハン」を置く。アセットの棚卸し（Asset Registry、寸法付き）から出せるもの（props）を選び、各アンカーを4方向から撮った写真で、人間と Claude がレベルの実際の姿を見てから組む。シーンの自動取り込み（実行時に組むレベルの PIE 内書き出し）は重いので見送り。
- D-25: 仕上げ（帯・タイトル・エンドカード・字幕・カットのつなぎ）を入れる。D-02 の例外として、音（D-19）と同じく定義の一部にする。`shots.yaml` の `finish:` と各ショットの `caption` / `transition` に書き、Cut で ffmpeg が焼き込む。fingerprint に入れないので撮り直しは起きない。つなぎは黒/白をはさむ形だけで、尺が変わるクロスフェードは入れない。自由編集の GUI は作らない。
- D-26: 音素材はプロジェクトの外のグローバルな音源ライブラリ（`~/Documents/ShotpilotLibrary/sounds/`、目録は `library.json`、`$SHOTPILOT_LIBRARY` で変えられる）に集め、そこから取ってくる。中身は Splice の購入済みサンプル（spliceclaw で `--confirm` なしで取得）。使うときはプロジェクトの `audio/lib/` にコピーし、shots.yaml には相対パスで書く（参照にしないのは、shots.yaml を唯一の正本に保ち、ライブラリの無い PC でもミックスできるようにするため）。アプリは音のパネルで検索・試聴・取り込みができ、音だけの指示では Claude が `lib:<id>` で選べる。
- D-27: リファレンスは open-design の `design-systems/` に倣い、実在ティザー1本を1パッケージ（`references/teasers/<id>/`：`TEASER.md` + `tokens.json` + `manifest.json` + `source/`）にする。動画とフレーム画像はリポジトリに入れない。
- D-28: 初回は「一気に作る」（open-design の production ターンに倣う）。制約（ブリーフ、ステージ、骨格、規則、ロケハン写真、ムードボード、仕上げの指針）を全部渡して plan を1回呼び、構成と仕上げを同時に出させ、最安の品質で撮って仕上げ込みで Cut まで通す。足りない下ごしらえ（ロケハン、ステージ、ムードボード）は先に埋め、2回目以降は使い回す。そのあとが検証の段で、人間が1カットずつ承認し、指して直す（D-13 の部分修正ループ）。エンドカードはブリーフにある事実だけを書かせ、日付やプラットフォームを作らせない。
- D-29: 集めたティザー（ゲームのみ 701 本）を ffmpeg で実測し、open-design の `craft/` と `design-systems/` に倣って、全ジャンル共通の型（`references/craft/`）とジャンル別パッケージ（`references/genres/<id>/`、horror / cozy / rpg / action / adventure）にまとめる。plan はブリーフの `genre` に合うパッケージを読み、骨格の hook と title の長さも同じ実測値から取る。分かったこと: 編集の山は第3四半分で、最後の四半分は最も遅い（単調な加速ではない）。shotpilot の既定のショット数（4.5 秒に1つ）は実測の下位4分の1に近い。
- D-30: アプリは1プロジェクト専用をやめ、ホーム画面から始める（open-design のホームに倣う）。左レールに「ホーム／すべてのプロジェクト／設定／最近のプロジェクト」、中央に「どんなティザーを撮る？」のプロンプト欄と種類（ティザー／ゲームプレイ）・エンジン（UE なし／UE5）・保存先、その下に例。送るとプロジェクトを作り（プロンプトは `teaser.pitch`）、Claude に接続済みならそのまま「一気に作る」（D-28）に入る。一覧は `<config>/shotpilot/projects.json` に場所だけを持ち、正本は各フォルダの shots.yaml のまま。UE5 の新規は .uproject の隣にフォルダを作り、マップは Content/ の .umap から選ぶ。開いているプロジェクトはウィンドウに1つで、studio の左上からホームへ戻る。
- D-31: ワークフローは「台本が先」にする（七号室の手作り v9 に倣う）。文字（カード・字幕・数え上げ・決まり・最後のメッセージ）を先に書き、各ショットはその1行の証拠として選ぶ。台本は `script:`（ショットの間のカードは `after:`、重ね文字は `on:`）で、Cut の並びは `script::layout` が決める。音は台本の行とショットに紐づけ（区間ごとの曲、行の SE）、Claude がライブラリ（D-26）から選んで書き込む。一気に作るは「台本と構成 → 音の設計 → 撮影 → Cut」の順。すべて編集的で、撮り直しは起きない。
- D-32: 音は撮り直し後も消さず、測る音量は出す音量にそろえる。再 plan（台本の置き換え、ショット id の付け替え）では、SE と曲の区間を id か位置で新しいショット・行へ引き継ぐ。サウンドチェックとアプリの試聴は、Cut と同じく `audio.loudness` に正規化したミックスで行う（全体の音量は `audio.gain` ではなく `audio.loudness` で決まる）。音だけの指示では、台本の行の `sfx` と `audio.music` も Claude に直させ、行を1つ選んだときはその行だけに絞る（コードで強制）。
- D-33: 構図の確認用に、ショットごとの絵コンテを画像生成で描く（D-23 で後回しにしたもの）。previz の線画（ガイドと見出しを抜いたもの）を下絵にしてカメラと配置を保たせ、写っているアンカーのロケハン写真とムードボードを参照に渡して、リアル寄りの1枚にする。`storyboard/<shot>/<look fp12>.png` に置き、take にはせず Cut にも使わない（ティザーの画はすべてゲームから撮る、は変えない）。Three.js での陰影付き描画は、シーンの形状を取り込んでいない（D-24）ので箱以上にならず、見送った。
- D-34: Cut は ffmpeg の `loudnorm` をかけず、`audio.loudness` に正規化・リミット済みのミックス（sound.rs）をそのまま 48kHz の AAC で載せる。動的 `loudnorm` は抑揚を圧縮し、出力を 96kHz にしていた（検査した音と出す音がずれる。D-32 の徹底）。音源のデコードはプロセス内にキャッシュし、`until` で止まる配置は届く長さだけをデコードする。
- D-35: 外部の参考（rea-video、ScrapeCreators の social-media-research-skills）はいまは取り込まない。あとで検討する候補は `research_notes/参考にできる外部プロジェクト.md` に残した：評価の留出セットと出典付きの真値、SE の画面イベントへの吸着検査、色と文字の実測項目、参照ティザーの選別を投稿元の中央値比で行う案。
- D-36: 一気に作ったあとは、人間が1カットずつ目で確かめて直す（D-22 の「検証するのは人間」を構図以外にも広げる）。その場所は「構成」の段のカット表で、Cut に出る順に1行1カット（台本のカードも行として挟む）。承認はワンタップか Enter、文字（見せるもの・台本）と秒数はその場で書き換え、カメラ・光・音の欄を指すと、その部分だけを Claude に直させる（範囲はコードで強制）。寄る／引く／広角／望遠／±0.5秒は Claude を呼ばずにコードで計算する。直したカットだけ previz を自動で撮り直し、行の中に「何が変わり、どれだけ撮り直したか」を出す。編集はすべて元に戻せ（Ctrl+Z）、戻すと前の take を使う。次の段は工程の区切り（台本の承認 → カット割り → 構図）と、一気に作るを区切りで止めること。
- D-37: ゲームの変化を検知して、写っているカットだけ撮り直す。調査で一番強い不満は「ゲームが変わるたびに全部撮り直す」で（reports/ゲームトレーラー制作の不満と困りごと.md）、似た製品はどれも「何が古いか」を判定しない（reports/トレーラー制作の類似プロダクトと解決策.md）。エンジンがレンダ中に写っていたもの（PIE の was_recently_rendered と、そのアセットの hard 依存）のパッケージを報告し、take がそのファイルの SHA-256 を持つ。中身が変わったカットだけが「GAME」（ゲームが変わった）になり、撮り直しはそのカットだけ。新しい take は `<fp12>~N/` に置き、中身を戻せば前の take を使う。fingerprint はゲームの中身を含めない（定義だけ）。レベルでの配置とコードの変更は対象外（PIE から元のパッケージに戻せないため）。
- D-38: 一気に作るは確認点で止まる（D-28 の変更）。アプリでは、台本と構成を組んで previz を撮ったところで止まり、人間がカット表で台本とカットを確かめて直し、「台本を承認して続ける」で音の設計→撮影→Cut に進む（「最後まで自動」も残す）。台本の承認は台本の文字と位置、各カットの目的・ビート・秒数と並びの指紋に紐づき、変わると外れる。カメラ・光・音では外れないので、台本を承認したまま「カメラだけ組み直す」（全カットのカメラだけを Claude に組ませ、他の項目はコードで守る）ができる。台本とカメラを別の呼び出しに分けることはしない（previz を出すにはカメラが要り、確認の場で両方見えるほうが速い）。
- D-39: ジャンルの型を骨格と仕上げに効かせ、「流行りの型」を選べるようにする。骨格の各カットの長さは、ビートの重みを実測の四半分ごとの編集密度で割って決める（忙しい四半分は短く、落ち着く最後の四半分は長い。D-29 の実測を骨格に反映）。色調に warm（コージー）・vivid（アクション）・cool（SF・ミステリー）を足し、台本の手法はジャンルを問わない一覧にした。流行りの型は、各ジャンルで 2025 年以降に最も見られたゲームのティザー 4 本（計 20 本、インディーと話題作を混ぜ、映画・TV・実写は除く）を、コンタクトシートと実測から分析したもの。brief.style で選ぶと、plan はその分析とリズムを読み、骨格は hook・title・密度の形をその型から取る。真似るのは構成とリズムと技法だけで、筋・キャラクター・文言は真似しない。アプリのブリーフにジャンルのカードと型のカード（リズムの帯つき）を置き、押せば保存する。
- D-40: ジャンルを増やすのは、20 本以上のゲームのティザーが集まったものだけ。キーワードで決まらなかった 305 本は Claude にタイトル・タグ・説明文を読ませて分類し、まだパッケージの無いジャンルに入ったものだけを `references/teasers/_genre_overrides.json` に残した（既存 5 ジャンルの標本と数値、手で書いた文は変えない）。足したのはストラテジー・シミュレーション（26 本、型 4 本）。SF（ゲームだけだと約 15 本）、パーティー・協力（21 本だがリズム・アイドル系が混ざる）、レース・スポーツ（17 本）、サバイバル（13 本）は見送り。照合の順は horror → cozy → strategy → rpg → action → adventure。
- D-41: 画面と案内の言葉では、映像の単位を「カット」と呼ぶ（カット表、カット検査、「このカットに指示」）。shots.yaml、コード、CLI、ドキュメントは shot / ショットのまま。数値や状態の表示（撮った・使い回し・古い・ゲーム変更・コマ）も日本語にし、品質名（previz / still / preview / final）とビート名（hook など）は用語として英語のまま残す。
- D-42: 指示の範囲に「文字・つなぎだけ」を足す（D-36 の拡張）。焼き込む文字（台本の重ね文字とカードの文字・種類・長さ、ショットの字幕）、つなぎ（黒/白）、明るさ（`exposure`）だけを Claude に直させ、全体への指示（仕上げのデザイン画面の欄）ではさらに色調・帯・書体まで直させる。範囲はコードで強制し、どれも編集的なので撮り直しは起きない（直したあとは「Cut で見る」で焼き込んで確かめる）。行の置き場所は変えさせず、タイトルとエンドカードは人間が書く（D-28）。画像（ロゴなど）や、行の種類とタイミングで決まる以上の動き（モーション）は足さない。指示の欄の下には、範囲ごとに押すと欄に入る例（送らない）と、送ると撮り直しが起きるかどうかを出す。カード（ショットの間の行）にも、文字・長さだけの指示欄を置く。
- D-43: 音は1つずつあとから微調整できる。BGM・曲の区間・カットの SE・台本の行の SE のどれにも、音量（`gain`）に加えて高域カット（`high_cut`、Hz より上を消すローパス）と低域カット（`low_cut`、Hz より下を消すハイパス）を書ける。フィルタは 24 dB/oct のバターワースを sound.rs のミックスの中でかける（ffmpeg は使わない。試聴・サウンドチェック・Cut が同じ音になる）。アプリの音パネルでは数値と一押しの値（8k / 4k / 1.5k、100 / 300）で直し、「高域を消して」「もう少し大きく」は音だけの指示で Claude がその音のキーだけを変える。編集的で、撮り直しは起きない。
- D-44: ロケハンは UE5 でもボタン1つ（とプロジェクトを開いたとき）で済ませる。アンカーが無ければ、UE を1回だけ起動してレベルからアンカーを取り込み（タグ付きのアクター、無ければ目立つものの候補から最大6か所。選び方は D-45）、アセットの棚卸しも同じ起動で行い、続けて4方向を撮る。アプリは UE5 のプロジェクトでロケハンを初めて開いたときに自動で始め（失敗しても繰り返さない）、一気に作る（D-28）も同じ入口を通る。自動で選んだアンカーは shots.yaml に書くので、人間が消したり名前を変えたりできる。
- D-45: 企画を open-design（nexu-io/open-design、Apache-2.0）の OD Next の計画ターンにほぼ倣って先に置く。流れは「企画 → ロケハン → ステージ → ムードボード → 台本と構成 → previz で止まる（D-38）→ 承認 → 音 → 撮影 → Cut」。企画では、欠けで目的が変わる・手戻りが出るときだけ質問フォーム（5問まで、推奨の既定値つき、「その他」は画面が足す）を出し、そうでなければ方向を1文で言い切った企画（目的・成果物・方向・手順・ビート表・前提・ロケハンで探すもの）を書いて、承認を待たずに制作へ進む。ルック（open-design の design-systems/ に倣う `references/design-systems/<id>/`、DESIGN.md 9節 + tokens + manifest、汎用の12本）とスキル（skills/ の SKILL.md に倣う `references/skills/<id>/`、全体の型14本と部分の型4本）を用意し、企画で Claude が説明文から選ぶ。構成を組むときは、選ばれた DESIGN.md とスキル本文を全文渡し、ルックの tokens で色調・帯・書体をコードで決める。プロジェクト自身の DESIGN.md（ゲームのブランド）があればそちらの文章を優先する。ロケハンの場所は、タグが無いレベルでは企画に合わせて Claude が候補から選ぶ（無理なら散らばった順）。実在ブランドの見た目は写さない（VoltAgent の集成も MIT だが商標は別）。自分のブランドをストアページやロゴから取り込む流れ（open-design の brand-extract）は次の段。
- D-46: 企画にビートごとの「どんな画か」（2〜6枚）を書かせ、企画のあとに「構成画を作る」ボタンを出す（押したときだけ画像生成。`concept/` に置き、参照に限る）。ロケハンは構成画に近そうな候補を先に撮り、撮った写真と構成画を Claude が見比べて「合う／だいたい／ない」を決める。「ない」ビートには別の候補を足して撮り直す（最大3周、1周に4か所まで）。見つかった場所と向きは、台本と構成を組むときにそのビートのカットの置き場として渡す。見つからないビートは雰囲気だけを使う。構成画があるとき、一気に作るはムードボードを作らない（構成画で代用）。生成画像をティザーの画には使わない（D-23）は変えない。
- D-47: ティザーのあとも発信は続く（調査で「古いトレーラーのまま出した」「外注した動画が古くなる」「ゲームが更新されたら撮り直す仕組みを自作した」）。そこで工程バーの最後に「公開」を置き、発信計画をチェックシートにする。3層で持つ。①節目の動画（発表・ゲームプレイ・デモ／フェス・ローンチ・アップデート・セール）は、動画ごとに隣の別プロジェクトとして作る（ブリーフ・props・アンカー・ステージ・ロケハン写真・ムードボードを引き継ぐ。アップデートトレーラーはカットと take も引き継ぎ、ゲームが変わったカットだけが撮り直しになる。D-13 を動画をまたいで効かせる）。1プロジェクト1本は変えず、1つの shots.yaml に複数の動画は持たせない（スキーマと state を崩さないため）。②アップデート連動は D-37 の検知から、変わったカットと撮り直し・アップデートトレーラーの作成を出す。③定期発信は間隔（既定7日）と投稿先を持ち、撮り直したカットと前回の投稿後に撮ったカットを候補に、take をそのまま静止画か1カットの動画で書き出す。縦型の短尺はまだやらない（カメラから組み直しになる）。チェック項目のうち、構図の承認・P0・ゲームの変化・Cut はプロジェクトから自動で判定し、残り（音なしで伝わるか、冒頭のロゴ、エンドカードの事実、ストア・SNS・プレスキット、種類ごとの1〜2項目）は人間が付ける。計画は `promo.json` で編集的、撮り直しは起きない。フェスの提出仕様は未確認なので、項目は「要項を確かめる」に留める。
- D-48: 修正（revise）にも、plan と同じ凍結した仕様を渡す（open-design の Design Spec を全経路で共有する考え方と、prompt-composition.md の「プロンプトを組む経路を全部挙げる」に倣う）。それまで revise は企画の方向・ルック・スキル・ブリーフ・規則を知らず、距離表とステージも「カメラだけ」を指したときにしか渡らなかった。指示が変えうるもの（画／文字／音）で渡す量を決め（`craft::edit_spec`）、画のときはそのカットのアンカーのロケハン写真も添える。8 経路に何が届くかをテストで固定した。
- D-49: ティザーの基準値（`references/craft/TEASER-BASELINE.md`）を置く。open-design の Design baseline とタスクプロファイル（hyperframes、motion-design）を言い換えたもので、主観を数値に置き換えた基準（文字の保持・量・置き場所・読みやすさ・事実）、ティザーで避ける「AI っぽさ」、「欠陥 → どう直すか」の表。plan と、画・文字の修正に渡す。読み時間（1.5 秒以上、日本語 4 字・英語 3 語で 1 秒 + 0.5 秒、数え上げは 1 秒）はコードで整え、人間が書いた行は `text.hold`（P1、出典あり）で示す。どれも編集的で撮り直しは起きない。
- D-50: 撮影後に1回だけ事実を確かめ、1回だけ直す（D-22 を動画の撮影だけ緩める。open-design の OD Next の動画の例外に倣う）。produce の初回のエンジンでの撮影のあと、各カットの中央フレームを Claude に1回見せ、被写体が写っているか（yes / partly / no）と何が遮っているかだけを答えさせる。no のカットだけカメラを1回直して撮り直し、そのカットだけ見直す。2周目はしない。結果は見た take と一緒に state.json に残し、カット表に `frame.blocked`（P1）として出す（承認は止めない）。previz では走らせない。Cut の長さとタイトルの文言は、コードで事実として注記する。
- D-51: 英語と日本語を PC の言語で切り替える。画面は日本語で書いたまま、PC の言語（WebView2 の `navigator.language`、OS の表示言語に従う）が日本語でなければ、`web/i18n.js` が画面に出た日本語を辞書（`web/i18n-en.json`、約 1250 件）で英語に置き換える。描画コードは触らない。辞書の見出しはソースから自動で抜き（`tools/i18n_extract.js`）、`${…}` の穴は型として扱う。ユーザーと Claude の文は訳さない（辞書に無い文は残り、自由な文が入る穴は `i18n-free.json` で区別し、助詞だけの型は使わない）。サーバーが送る日本語（工程名、注記、サウンドチェック）と参照データの名前・説明も同じ辞書で訳す。英語のエラーと検査の説明は英語のまま。Claude の出力の言語はプロンプトの言語に従う（英語で書けば英語で組む）。確かめるときは `?lang=en`（`?lang=auto` で戻す）。
- D-52: 文字の組み方と書体を、open-design の `craft/typography.md` と hyperframes の `typography.md` の形で持つ。手元のティザー 77 本を 1 コマずつ測り、規則集 `references/craft/TEASER-TYPE.md` と書体の目録 `references/fonts/`（Google Fonts の日本語 68 書体すべてと欧文の候補 61 書体、定番すぎる書体 34。漢字の収録は実ファイルで数えた）を置いた（reports/文字デザインと書体の調査.md）。ルックの tokens は目録の書体を `Family:weight` で持ち、ジャンルの定番と言語モデルの既定（Cinzel、Inter、Bebas Neue、既定の Noto など）をやめた。plan と `shotpilot design <id>` で `finish.fonts`（display / body / latin）と `finish.title_size` に書く。描画は書体を Google Fonts から 1 回だけ取ってきてキャッシュし（目録の OFL の書体だけ。システム書体は読むだけ）、書体に無い字を含む行はその行だけシステム書体で描く。大きさは実測に合わせ、英語の添え書きを画面高さの 2.5% に、字幕を約 5% に上げ、タイトルはルックごとに 10〜20% にした。タイトルはゲームのロゴ画像（`finish.logo`）で出せる。D-42 の「画像を足さない」を、タイトルのロゴに限って変えた（測ったタイトルの約 9 割がロゴだったため）。台本を書く側の規則（1 行 9〜11 字、見出しの行は句点で終えない、数字は半角、英語の添え書きは要る行だけ）は、TEASER-TYPE.md の 10 節だけを plan と画・文字の修正に渡す（OD Next が skill の求める craft の節だけを差し込むのに倣う）。どれも編集的で、撮り直しは起きない。アプリでは、ルックを選ぶと書体が入り、仕上げのデザイン画面でロゴ画像を選べる（プロジェクトの外の画像は `art/` に写す）。
- D-53: 文字の動きとつなぎを、閉じた語彙と実測の既定値で持つ（D-42 の「行の種類とタイミングで決まる以上の動きは足さない」を変える）。open-design の motion-design / hyperframes に倣い、Claude は語彙から選ぶだけで、秒数はコードが決める。入りは cut・fade・flicker・focus・slam・pop・type・wipe・glitch、保ち方は still・drift・glow、抜けは cut・fade・glitch、つなぎに whiteout と glitch を足した（どれも尺を変えず、クロスフェードは入れない）。ジャンルごとの既定（`references/motion/profiles.json`、日本の PV の型を horror-ja・adventure-ja・rpg-ja・action-ja として別に持つ）は、33 本を 1 コマずつ見た記録と、736 本を明るさから自動で測った値（黒地の文字の入りの半分はカット、フェードの中央値 0.5 秒、RPG が最も遅い 0.75 秒、ホラーは黒へカットで 79%、1 秒に 3 回を超えるフラッシュは 0 本）から決めた。12 のルックは tokens の `motion` でどれかを土台にして上書きし、plan と `design <id>` とアプリでルックを選ぶと `finish.motion` に入る。ユーザーの意図は、plan の `motion`（勢い・日本の PV の型・使わない動き）と、全体への指示（「もっと静かに」「フラッシュはやめて」）で直す。台本の行は `motion:` で自分の入り方を選べる。入りは行の表示時間の 35% まで、抜けは 25% までに収めて読む時間を残し、1 秒に 3 回を超えるフラッシュはカット検査の P0（`flash.rate`、WCAG 2.3.1 と NHK・民放連のガイドライン）にする。動きの書き方（MOTION.md の 6 節）だけを plan と画・文字の修正に渡す。`finish.motion` が無ければ、それまでと同じ動きになる。編集的で、撮り直しは起きない。
