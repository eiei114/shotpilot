# 工程を知る AI が、1カットだけ撮り直す

ゲームトレーラーの工程は「ブリーフ → 複数案のスクリプト → ショットリスト → キャプチャ → 編集 → 音 → 仕様に沿った書き出し」で、新規キャプチャを要するノートが最も高くつく。shotpilot に AI を入れるなら、`shots.yaml` を「スクリプト兼ショットリスト」の正本に据え、AI には案出し・カバレッジ確認・決定論的な lint を、人間には構図の承認・音楽の趣味・フックの選択・真実性の確認を任せる分担が、集めた証拠と最も整合する。裏付けの強い規則は少数で、「ミュートでも成立」「冒頭にロゴやメニューを置かない」「コア映像を早く見せる」「Steam はティザーを別カテゴリとして扱う」に絞られる。ショット長（ASL 1.5〜3 秒）、フック尺、ビート同期率、構図の閾値といった数値は、ほぼすべて推論で、ゲームトレーラーを実測した研究も見つかっていない。したがって shotcheck は、出典のある規則を error（P0）、推論の閾値を warn（P1/P2）に分け、ffmpeg のシーン検出で実トレーラーを測って校正する二層構造にするのが妥当である。参照コーパス、lint、1回リトライ、型の穴埋めを先に作り、eval ハーネスは小さく始める。なお取得できた出典の多くは実務者の発言の二次要約で、Derek Lieu 本人の記事や GDC 講演の本文は読めていない。

## 業界の工程は「複数案から選ぶ」と「差し戻しが撮り直しを生む」で決まる

実務者の工程像は、Derek Lieu のガイドの章立てが最も整っている。事前準備（制作チェックリスト、開発者に依頼する素材）、コンセプト、キャプチャ、編集、仕上げ（アイトレースや強調）、最終確認（よくある欠陥、字幕、命名、コンソールの仕様確認）と進む ([gcores 翻訳](https://www.gcores.com/articles/151970))。ただしこれは目次の翻訳であって、各段の詳細は未取得である。コンセプト段で最初に問う事柄は具体的で、ゲーム内容は十分にあるか、コアと比較対象は何か、誰向けか、マーケティング上のどの時期か、物語型かゲームプレイ型か、概念が分かりにくく文字通り説明が要るか、引用できるレビューはあるか、コンソール対応が要るか、である ([gcores 翻訳](https://www.gcores.com/articles/151970))。これはそのまま shotpilot のブリーフ質問の雛形になる。

キャプチャ専門ベンダーの工程は、クライアントの試作ビルドを長時間プレイし、薄いブリーフから複数のスクリプトを書き、実現性を調整してクライアントが1案を選ぶ。続いてショットリストと社内キックオフ、デバッグツールの調査、キャプチャ、素材の取り込み、足りないカバレッジの特定と編集への引き渡し、野心的な V1 から承認版へ反復、という順である ([Aftermath](https://aftermath.site/video-game-trailer-capture-director-maker/))。CG 寄りのトレーラーでは、脚本・ストーリーボード・簡易ビジュアライゼーション・コンセプトアート・カラースクリプト・アニマティックという粗い時間付き試作品で物語の流れを固めてから高価な制作に入る ([Room 8 Group](https://room8group.com/news/how-trailer-pre-production-augments-your-game-development-and-marketing-efforts/)。ベンダーの自社説明である)。映画の previz も「pitchviz → previz → techviz → postviz」と段階を分け、構図は3Dで仮組みして監督が承認するまで磨いてから、実写と VFX の配分を決める ([VFXWorld](https://d1xfgk3mh635yx.cloudfront.net/vfxworld/prevalence-previs))。

手戻りの原因は明確に報告されている。V1 へのノートで新規キャプチャが要る場合、ビルド更新で既存素材を撮り直す場合、スケジュールや範囲の変更、ビルドの制約である ([Aftermath](https://aftermath.site/video-game-trailer-capture-director-maker/))。Blizzard は、タイミングを外すとシーン全体を撮り直す事態を避けるため、シーンを正確に再生できる Sequencer 風のツールを使う ([Inven Global](https://www.invenglobal.com/articles/25875/everything-blizzard-says-about-creating-gameplay-trailers)。記事の日付表記に不審な点があり未検証扱い)。ここに shotpilot の位置が出る。ショットを YAML で定義して決定論的に再生すれば「タイミングを外したら全撮り直し」のコストが消え、fingerprint でビルドや定義の変更に影響されたショットだけが古くなる。Epic も、分散レンダの最小単位は1つのカメラカットであり、リアルタイム機能は前フレームの情報に依存するため複数マシンで共有できないと述べている ([Epic: command line rendering](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-command-line-rendering-with-move-render-queue-in-unreal-engine))。ショット単位の粒度は公式の説明とも噛み合う。ただし公式のコマンドラインにはショットを選ぶ引数が無く、ショット単位レンダは Python エグゼキュータ相当の自作になる、という点は実装上の前提として押さえておく。

一方で、レビュー製品の標準は「バージョン + ショット + フレーム + 注釈」のノートで、SyncSketch は ShotGrid のプレイリストを取り込み、フレーム精度の注釈つきノートを返せる ([SyncSketch](https://support.syncsketch.com/hc/en-us/articles/32394066503316-Syncing-Playlists-and-Notes-with-ShotGrid))。shotpilot の「フレーム/領域を指して自然言語で直す」は同じデータ形で、宛先が人間から Claude に変わるだけである。業界ではノートを人間が読んで手で直すため、ノートからの自動修正は今回の調査では見つからなかった（不在の証明ではない）。fingerprint による変更ショットだけの再レンダ、Sequencer の人手編集を正本に戻す三方比較も同様に、調べた範囲では先行例が見つからなかった。

## 構成とテンポで確かな根拠があるのは「冒頭」と「ミュート」だけ

構成の標準は、コールドオープン、3幕（導入、エスカレーション、クライマックス）、button で、現代の多くのトレーラーは5パートを使う ([Jonny Elwyn](https://jonnyelwyn.co.uk/film-and-video-editing/how-to-edit-a-movie-trailer/))。shotpilot の `hook → establish → escalate → title` はこの型に素直に対応する。ただしコールドオープンの長さは作品で大きく違い、Joker ティザーは約9秒、Hobbs & Shaw は約45秒で、どちらも映画の例である ([Jonny Elwyn](https://jonnyelwyn.co.uk/film-and-video-editing/how-to-edit-a-movie-trailer/))。「フックは3秒以内」のような強い規則は、出典からは導けない。

ゲームに固有の根拠は Steam 公式が最も強い。最初のトレーラーは主にゲームプレイにすること、ストア閲覧者は10秒未満で印象を決めること、HUD が見えると有益なこと、音声オフでも成立させることが明記され、シネマティック型はロゴやタイトル画面が混ざりゲームプレイが少ないと位置づけられる。一方でティザーは「タイトル/IP に焦点」を当てるものとして別カテゴリになっている ([Steamworks](https://partner.steamgames.com/doc/store/trailer))。実務者側も一致する。Lieu は最初の数秒でゲームプレイを見せ、遅いイントロ、タイトルカード、ロゴ、長い establishing shot を避けるよう勧める ([WN Hub](https://wnhub.io/news/analytics/item-237)。GameDiscoverCo 記事の二次要約)。Zukowski の観察では、多くの人が進行バーをクリックして生のゲームプレイを探す ([GameDiscoverCo](https://newsletter.gamediscover.co/p/game-trailers-breaking-down-a-key)。検索要約）。

ここに shotpilot 特有の緊張がある。30〜60秒のシネマティックなティザー（hook → establish → escalate → title）は、Lieu や Zukowski が「ストア最初の動画としてインディーに勧めない」型に近い。Steam が Teaser を独立カテゴリにしているので正当な形式だが、証拠は「ゲームプレイ中心のトレーラーと組み合わせる」ほうを支持する。したがって shotcheck は、`gameplay-first` を全ティザーに強制せず、トレーラーの種別（teaser / gameplay）を brief で宣言させ、種別ごとに規則の重みを変えるべきである。teaser では「冒頭にロゴ・メニューを置かない」「title は終盤」を維持しつつ、「t=0 からコア映像」は P1（警告）に落とす。gameplay では P0 にする。

ショット長とテンポは、規則の根拠が最も薄い領域である。130本のハリウッド予告を扱った学位論文は平均ショット長が60年で短縮したと報告するが、ASL の数値は未取得で本文も403で読めていない ([Temple ScholarShare](https://scholarshare.temple.edu/items/0ab4cb95-3dcb-4405-b404-296c897d6ab3)。検索要約）。Masterclass のトレーラーではショット長はほぼ1〜2秒だった、という単一例がある程度である ([Jonny Elwyn](https://jonnyelwyn.co.uk/film-and-video-editing/how-to-edit-a-movie-trailer/))。ゲームのトレーラーを測ったデータは見つからなかった。音については、編集者が編集前に曲を知っておくことで転換点が決まる ([Jonny Elwyn](https://jonnyelwyn.co.uk/film-and-video-editing/how-to-edit-a-movie-trailer/))。Lieu のガイドも遷移を音楽的・視覚的・ストーリー的・「music stop」に分類し、アイトレースで滑らかにつなぐとする ([gcores 翻訳](https://www.gcores.com/articles/151970)。目次のみ）。Joker ティザーはライザー、ドローン、ベルヒット、意図的な無音を使う ([Jonny Elwyn](https://jonnyelwyn.co.uk/film-and-video-editing/how-to-edit-a-movie-trailer/))。数値規則は無いが、shotpilot は既に BGM を `audio:` に持つので、カット位置と拍の誤差は機械検証できる。

ジャンル別の型は、ほぼ空白である。ホラーが「遅い establishing → ショットが短くなる → ジャンプスケアは後半」という通説と、映画の予告の尺統計でホラーと SF が最も短いこと ([Stephen Follows](https://stephenfollows.com/p/long-average-movie-trailer)) 程度しか取れず、前者の出典は低品質だった。アクション、コージー、パズルの専用規則は未発見である。「ジャンル別 TRAILER.md」を作るなら、規則の出典を空欄にせず、実測値で埋める前提で作る必要がある。

## 撮影のセオリーは計算できる部分だけが堅い

撮影側の出典は、StudioBinder、Mascelli、Katz、Blain Brown が取得できず、書籍レベルの主張は直接検証できていない。そのため、確かなのは定義と幾何であり、数値の多くは慣習または推論である。

ショットサイズは、レンズでなく「フレームが身体のどこで切れるか」で定義される（EWS から ECU まで）。同じ CU でも 20mm では顔の中心が誇張され、200mm では平坦で背景が近く見える ([Filmdaft](https://filmdaft.com/the-most-frequently-asked-questions-about-camera-shots-and-camera-angles/))。したがってプランナは「サイズと焦点距離から距離を解く」べきで、`d = f × H_visible / h_sensor`（h_sensor は出力アスペクトで決まる実効センサー高）が成り立つ。UE の CineCamera のフィルムバックはミリ単位で、水平 FOV は焦点距離とセンサー幅から導かれる ([Epic API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/CinematicCamera/FCameraFilmbackSettings?lang=en-US))。「Super 35」は単一の寸法ではなく、フォーラムでは寸法が食い違い、プリセットでなく手入力で合わせたという報告もある ([UE forum](https://forums.unrealengine.com/t/cinema-camera-focal-length-incorrect/367059))。よって実際のフィルムバックを必ず読む。S35（幅 24.89mm、16:9）で身長 170cm の人物を想定した計算では、CU（可視高 約40cm）は 50mm で約 143cm、85mm で約 243cm、FS は 35mm で約 488cm になる。この計算値は幾何から導いたもので、各サイズに割り当てる可視高の目標値（CU で身長の約 0.23 倍など）は慣習による推論である。

レンズの印象は DP の証言と解説ブログから支持される。広角は周辺を歪ませ、部屋を広大で威圧的に見せる。望遠は奥行きを圧縮し、被写体を孤立させる。ホラーの『The Invitation』では CU でも 29mm など広めのレンズを使い、環境が人物を圧倒するようにした ([ASC](https://theasc.com/article/scare-tactics))。ネガティブスペースが孤立や不安を生む点も同じ系統の二次情報で支持される ([Indie Cinema](https://blog.indiecinema.co/?p=892229))。ただし「12〜18mm は超広角」といった帯域の境界や、「CU で 24mm 未満なら警告」のような閾値は慣習である。

カメラムーブは、すべてのショットに動機付けが要る。静止も移動も同様で、被写体の動きがあれば truck in は十分に動機づけられ、truck out のほうが「不自然」とされる ([Grammar of the Shot](https://www.oreilly.com/library/view/grammar-of-the/9780240521213/Chapter06u.html))。ゆっくりした dolly in は人物の感情状態に引き込み、dolly out は発見や開示を強調する。クレーン/ジブは壮大な開始と終了に向く ([Filmdaft](https://filmdaft.com/the-most-frequently-asked-questions-about-camera-shots-and-camera-angles/))。この意味づけは shotpilot の `move` 語彙（static、dolly_in/out、truck、crane、orbit）にそのまま写せる。移動量や速度（dolly 量は開始距離の15〜40%、orbit は 3〜6 秒で15〜45度など）は出典のない調整用の既定値であり、数値は校正の対象である。ズームではなくカメラ移動を使う、というのも「ズームは平坦化し、ドリーは遠近を変える」という説明に基づく方針にすぎない。

カットの規則は、出典が最も明確なところである。30度規則は、同じ被写体を切り返すとき、カメラを30度以上動かさないとジャンプカットに見えるというものである。焦点距離の変化が約20mm未満で同じ角度なら似て見えるという変種もあり、軸上のカット（同角度）は例外として扱われる ([Wikipedia](https://en.wikipedia.org/wiki/30-degree_rule))。180度規則は、2人を結ぶ軸の片側にカメラを留めて画面上の位置関係を保つもので、Godard や『シャイニング』のように意図的に破る例があり、軸を渡る正当な手段（被写体の移動、ショット内での移動、軸上の中立ショット、カットアウェイ）も整理されている ([Filmdaft](https://filmdaft.com/understanding-the-180-degree-rule-in-media/))。注意点として、これらは物語映画の会話場面から来た規則で、2秒前後のモンタージュ型ティザーにそのまま当てはめてよいとは限らない。ポスト・コンティニュイティの編集はジャンプカットを意図的に使う ([Wikipedia](https://en.wikipedia.org/wiki/30-degree_rule))。lint では30度規則を「同一アンカーへの隣接ショットで、方位差・サイズ段差・焦点距離差のいずれも不足」という条件の P1 とし、180度規則は2アンカー間に軸が定義できる場合だけ検査するのが現実的である。

仕上げ側では、フレームレートと露光は慣習で、24fps で 180 度シャッター（1/48 秒）が標準的な説明であり、60fps で同じブラー量を出すなら 144 度シャッターになる ([DIY Photography](https://www.diyphotography.net/?p=309010))。納品は Steam 推奨の H.264 + AAC、最大 1920×1080、30 または 60fps、5,000kbps 以上、16:9 である ([Steamworks](https://partner.steamgames.com/doc/store/trailer))。UE のモーションブラー量とシャッターの対応は未検証である。

## 工程ごとに、AI が出す案、人間が決める判断、正本を分ける

前節までの証拠を shotpilot の工程に写すと、次の分担になる。基準は二つで、第一に「安い段階の選択」（複数案から選ぶ、アニマティック相当を見る）は人間が行い、AI が案を用意する。第二に「コスト構造が高いところ」（新規キャプチャ）は、手前の安いゲートで承認を取ってから通す。この分担は、構図は監督が承認するまで磨く ([VFXWorld](https://d1xfgk3mh635yx.cloudfront.net/vfxworld/prevalence-previs))、自動編集は「第一稿」止まり ([Python Libraries](https://pythonlibraries.substack.com/p/ai-powered-video-editor-with-automatic))、という弱い証拠とも整合する。ただし「AI に任せたくない判断」を実務者が語った一次証言は取得できておらず、この分担は証拠からの推論である。

| 工程 | AI が行う | 人間が判断する | 正本 |
|---|---|---|---|
| ブリーフ | 既定値つきの質問（種別、尺、対象、コア、必見機能、素材、利用可能な曲とロゴ） | ゲームに十分な内容があるか、種別の決定 | `shots.yaml` の brief ブロック（新設） |
| スクリプト/ビート | 型の穴埋めで2〜3案（hook → establish → escalate → title） | 1案を選ぶ、フックの選択 | `shots.yaml` のビート列 |
| 絵コンテ/ショットリスト | 各ショットのアンカー・サイズ・レンズ・ムーブを提案 | 構図の承認 | `shots.yaml` |
| previz/still | なし（決定論的描画） | 構図承認のゲート | `render/` の previz と still（導出物） |
| キャプチャ | ショット単位の再レンダを依頼するだけ | preview/final を撮る判断 | `render/<shot>/<quality>/<fp12>/` |
| 編集 | カット順と拍の整合の検査、粗編集の提示 | ペースとフィールの最終判断 | `shots.yaml`（順序と尺）。NLE の編集は持たない |
| 音 | 曲の候補検討、SE の配置、サウンドチェック | 曲の趣味、ミックスの最終判断 | `audio:` と各ショットの `sfx:` |
| 仕上げ | Steam 仕様の書き出し（codec、fps、音声レート）と検査 | 真実性の確認（実ゲームと違う内容を見せていないか） | `cut/` の出力 |
| レビューと修正 | フレーム/領域つきノートを `revise` で編集案に変換し検証 | ノートを書く、編集案を承認する | `shots.yaml` と `.shotpilot/state.json` |

編集の正本について、実務ではペースと音楽同期の真の正本は NLE のタイムラインであり、shotpilot は録画後の編集を作らない（D-02）。この前提を保つなら、`shots.yaml` の尺と順序、`audio:` の位置を「編集の正本」に格上げし、NLE で追い込む必要が出たら「書き出して終わり」にするのが筋である。Sequencer での人手の修正は `pull` で戻せるので、人間が Sequencer で直した差分は黙って上書きされない。この三方比較は「機械案を人間が上書きしても機械が黙って戻さない」という信頼の条件を満たす。

## 薄く盲目なプロンプトは、参照コーパス、lint、1回リトライで底上げする

現状の弱点は、`plan` のプロンプトがアンカー名と座標しか渡さず、品質も再現性も低いことである。open-design 型の方針は、出典の裏付けの強さで二層に分けて入れるとよい。

第一層は出典のある規則で、これは lint の error（P0）とプロンプトの hard rule にする。冒頭ショットがロゴ・メニュー・タイトルカードでない、title が先頭付近にない、音声なしで成立する（音声依存の要素が無い、字幕や視覚で意味が通る）、`shots.yaml` が型（hook → establish → escalate → title）に沿う、納品仕様が Steam 推奨に合う、同じ被写体への隣接ショットが30度規則の最低条件を満たす（ただしモンタージュでは意図的な破りを許す宣言を設ける）、動きに動機がある、といった内容である。ここで出典の強さは「強」の Steam 公式を除けば「中」止まりであり、Lieu 本人のテキストで裏を取る作業が残る。

第二層は推論の閾値で、これは warn（P1/P2）のみにし、ffmpeg のシーン検出で実トレーラーを測って校正する。対象は、ASL（暫定 1.5〜3 秒）、エスカレーション区間でショットが短くなること、最長/最短ショット比、hook の尺、title の尺（暫定 2〜4 秒）、拍とカットのずれ、ネガティブスペースやヘッドルームなどの構図閾値、移動量と速度、ムーブの組み合わせ（dolly_in の連続など）である。校正の手順は単純で、Lieu が挙げたり、既に shotpilot の sound check が比較に使っているローンチ映像7本について、`ffmpeg -vf "select='gt(scene,0.3)',showinfo"` でカット時刻を取り、ASL・最長/最短比・全体尺・最初のカット位置を集計して、各閾値を実測の分布（例えば四分位）に置き換える。これで推論の閾値が「実測に基づく既定値」に変わる。注意点は二つある。映画のデータはゲームに当てはまるとは限らず、ゲームは HUD や操作を読む時間が要るので ([gcores 翻訳](https://www.gcores.com/articles/151970)で Lieu が認知負荷に触れている)、校正対象はゲームのトレーラーに限る。また、シーン検出は暗転やフラッシュに誤反応するので、閾値は手作業で数本確かめる。

参照コーパスは、open-design の DESIGN.md に倣った「Inspired by <実在のトレーラー>」形式の TRAILER.md にする。各ファイルに Do/Don't と実測値（ASL、尺、title 位置、カット数）を書き、実測値は ffmpeg で取った数字だけを入れる。測れていない項目は空欄にして `unmeasured` と明記し、推論を事実のように見せない。ジャンル別の型は出典が空白なので、ジャンルでなく実在のトレーラー単位から始めるほうが誠実である。型の穴埋めテンプレートは、ショット数、各ビートの尺配分、サイズの段階（例えば hook は WS/MS、escalate は MCU/CU に縮む）を固定し、モデルが座標・レンズ・ムーブを埋める。これで、モデルが弱くても骨格は崩れにくい。ここで検証すべき主張は「Haiku でも合格率が上がる」で、これは eval ハーネス（固定ピッチ × N 回 × モデル → 合格率）でしか示せない。

shotcheck の出力は、機械可読な findings（ルール ID、重要度、対象ショット、実測値、閾値）にして、モデルへ1回だけ差し戻す。リトライを1回に限るのは、コストと非決定性を抑えるためで、2回目以降の改善は小さいと見込まれるが、この見込みは未検証であり eval で確かめる。差し戻しで編集してよい範囲は、既存の方針どおりコードで強制する。P0 が残った場合は黙って通さず、画面に未解決として出す。

## 優先順位は「測る・縛る・見せる」の順

開発者は1人である。最優先は、デモの主張（3番目だけ再レンダ、他は触らない）を壊さないことで、そのうえで次の順に取り組む。

まず shotcheck の P0 規則と findings の形を作る。出典のある規則（冒頭にロゴなし、title は終盤、型の順序、サイズ/アンカーの幾何）から始める。幾何は `geometry.rs` に近く、依存なしで書ける。並行してローンチ映像7本の ffmpeg 測定を走らせて、閾値の初期値を得る。次に、型の穴埋めテンプレートと、`plan` のプロンプトへの参照コーパス（craft 規則と TRAILER.md 数本）の注入、lint 結果を1回差し戻す経路を入れる。ブリーフ質問と既定値は、UI を作らず `plan` の入力として受け取る最小形にする。その次に eval ハーネスを小さく作る（固定ピッチ3〜5本 × 3回 × 2モデル。合格率とP0違反数を出す）。ここで Haiku と上位モデルを比べ、改善が出ていなければ原因を分析する。最後にデモ動画と README、字幕「全部は撮り直していません」を確かめる。1ビート3バリアントは余力があれば行う程度にとどめる。

先送りにするものも明確にする。ジャンル別 TRAILER.md の網羅、VLM 審判による構図の自動採点、複数人のレビュー管理、ショット単位の注釈履歴、postviz と VCam は作らない。構図の自動採点は研究の評価法（VLM 審判、人手のペア選好）に倣えるが ([Moonlight review](https://www.themoonlight.io/review/stable-cinemetrics-structured-taxonomy-and-evaluation-for-professional-video-generation)。一次論文未確認)、今回の範囲を超える。

## Conclusion

今回の調査で見えたのは、業界の知恵の大半が「何をすべきか」の方向を支える一方で、「何秒か」「何度か」を支える数値がほとんど無いことである。強く裏付けられた規則（冒頭とミュート、ティザーとゲームプレイ型の区別、30度/180度の定義）と、ASL や構図の閾値のような推論を、同じ重みで lint に入れると、モデルを誤った自信で縛る。出典の強さに応じて error と warn を分け、warn は実測で置き換える、という運用が、shotpilot の「AI の提案を検証して通す」設計にそのまま乗る。

もう一つの含意は、shotpilot の競争力が AI の生成力でなく、周囲のループ構造にあることだ。MCP 系の UE エージェントは Sequencer や MRQ の遠隔操作までは届いても、状態管理、再レンダ判定、三方比較までは持たない、と今回の資料からは見える（網羅調査ではない）。AI に任せる工程を案出しと検査に絞り、承認と趣味と真実性を人間に残すことで、「AI が組み、人間が1カットだけ直すと、その1カットだけ撮り直る」という主張が、品質の面からも成り立つ。未解決の最大の課題は、Lieu 本人の記事、GDC 講演、ゲームトレーラーの ASL 実測が取れていないことで、これは実装の前に ffmpeg 測定と原文確認で埋められる。
