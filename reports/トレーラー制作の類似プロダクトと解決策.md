# 撮り直しの判定層は誰も持たない

調査した範囲では、**「定義の指紋から古いショットを判定し、そのショットだけ撮り直し、承認を画の変化に結びつける」層を、製品としても研究としても持つものは見つからなかった**。不満ごとに見ると、「撮影の再現性」はエンジンのリプレイや固定 FPS が部分的に、「レビュー」は Frame.io や Kitsu が成熟して解いている。一方、ゲーム変更後の撮り直しは、プロの現場でも「ノートが来たら担当者が撮り直す」という人手運用にとどまる。「何を見せるか決められない」は、AI 絵コンテや台本分割ツールが入口を作ったが、出力は生成画像で実ゲームの画ではない。いちばん近い競合は Kuaishou の Cutscene Agent(論文)で、UE 内で LLM が Level Sequence とカメラを組むが、正本は Level Sequence 側で、変更検知も承認ループもない。最大のリスクは Epic 公式の UE 5.8 MCP と Aura のような汎用エージェントで、「UE に Claude をつなぐ」こと自体はもう差別化にならない。勝負どころは shots.yaml・fingerprint・承認の三点セットを実演で見せることに絞られる。ただし「他にない」は不在の証明ではない。公式ドキュメントを取得できなかった箇所が多く、価格にも食い違いがあるため、提出文では断定を避けるべきである。

## 不満ごとの現状:部分的に解かれ、中心は空いている

前回の調査では、需要の重心は編集や費用ではなく、構成の決定とゲーム変更後の撮り直しにあった。「ゲームが変わるたびに撮り直す」証言は独立した複数のスレッドに現れ、開発者自身が「I just scripted code to play and change scenes and simply just screen recorded that. Now I just rerun it with game updates」と自前の再実行で対処している ([Reddit](https://www.reddit.com/comments/1vh629o/_/p22xbzh/))。ただし「変わったショットだけ再レンダしたい」という明示的な要望は1件も見つかっていない。以下の表は、今回の調査で見つけた解決策を不満ごとに並べたものである。

| 不満 | 誰がどう解いているか | まだ解かれていないこと |
|---|---|---|
| 何を見せるか決められない | プロは「台本を複数案書く → クライアントが選ぶ → 撮れる範囲に合わせて直す → ショットリスト」の順で、キャプチャディレクターがビルドを遊び込んで突き合わせる ([Aftermath](https://aftermath.site/video-game-trailer-capture-director-maker/))。AI 側は LTX Studio や Katalist が脚本をシーンとショットに自動分割する ([diyai.io](https://diyai.io/ai-tools/video-generation/ai-storyboard-generator/))。構成の型は助言記事に溢れる(例: Hook 0〜5秒 / Core Loop / Escalation / Title)([Steam Page Analyzer](https://www.steampageanalyzer.com/blog/steam-trailer-best-practices)) | 「撮れるか」の突き合わせは人間のまま。AI の絵は生成画像で、実ゲームの画ではない。ビートを構造化データで持つゲーム向け製品は見つからなかった |
| ゲーム変更のたびの撮り直し | プロは人手で再キャプチャし、EA は毎朝「最新ビルド」を確認する ([CGW](https://cgw.com/Press-Center/In-Focus/2021/EAs-Game-Capture-Artists-Bring-Battlefield-2042-.aspx))。UE の MRQ は `job.shot_info` の `enabled` を Python で切る回避策がある ([UE フォーラム](https://forums.unrealengine.com/t/how-to-exclude-certain-shots-from-a-mrq-rendering-via-python/2563979))。Houdini PDG は dirty 判定で変更分だけ cook する ([SideFX](https://www.sidefx.com/docs/houdini/tops/cooking.html)) | 何が古いかを内容から判定してゲームの撮影に適用するものは見つからなかった。PDG は出力ファイルの有無が中心で、入力内容のハッシュではない |
| 撮影の再現性 | UE の Replay System は「producing gameplay trailers or in-game cutscenes」に役立つと Epic が明記 ([Epic](https://dev.epicgames.com/documentation/unreal-engine/using-the-replay-system-in-unreal-engine))。Godot の `--fixed-fps` は delta を一定にする ([Godot](https://docs.godotengine.org/en/latest/classes/class_moviewriter.html))。Blizzard は Sequencer で同じシーンを任意の時点から再生する ([Inven](https://www.invenglobal.com/articles/25875/everything-blizzard-says-about-creating-gameplay-trailers)) | リプレイはゲーム側の協力が前提で、コードやアセットが変わると使えなくなる可能性が高い(推測)。固定 FPS は物理や乱数の非決定性を解かない |
| エンジンの録画ツールの使いにくさ | 周辺プラグインは補助に徹する。MRQ Frame Picker はキーフレームだけの MRQ キューを作る ([UE フォーラム](https://forums.unrealengine.com/t/alfredo-mendez-movie-render-queue-frame-picker-keyframe-render-tool/2741460))。Trailer Camera Toolkit は「no Sequencer, no editor required」でゲーム内から撮る ([UE フォーラム](https://forums.unrealengine.com/t/altar-creative-trailer-camera-toolkit/2690110)) | Take Recorder の取りこぼし、MRQ のウォームアップ、Lumen・TSR のアーティファクトは、フォーラムの回避策のまま。Unity の Sequences は Unity 6.1 でサポート終了予定 ([Unity](https://docs.unity3d.com/Packages/com.unity.sequences@2.1/manual/features.html)) |
| 撮影と編集の往復 | EA は選んだドーリーズを Frame.io に上げ、リードがノートを書く。制作会社は窓口を1人にしてノートを一本化する ([Fast.io](https://fast.io/resources/video-feedback-tool/))。Boords は Premiere / Resolve 向け XML や After Effects の .jsx を出す ([Boords](https://boords.com/export)) | ノートは動画のタイムコードに付き、人間がショットへ読み替える。Boords の書き出しは「その時点のコピー」で、編集ソフトで直した結果は戻らない |
| 外注の質と費用 | 低価格帯は「クライアントが映像を撮って渡す」前提で成り立つ。小規模サービスはティーザー $150〜250 ([Pixune](https://pixune.com/blog/how-much-does-a-video-game-trailer-cost/))、専門会社は 1分で $5,000〜$20,000+ | キャプチャが重く、遅く、人手依存という根本は残る。構成の判断は外注に渡せない |

## 周辺産業の実践は「撮る」「見る」を支え、「古さの判定」は持たない

UE 標準の Sequencer は Shot Track とサブシーケンスでショットを構造化し、Take で版を切り替えられる。しかし Take は「just another version of a subsequence (or shot)」にすぎず ([UE フォーラム](https://forums.unrealengine.com/t/sequence-takes/436206))、同じ入力から同じ映像を保証する仕組みではない。MRQ では、ショットを除外する方法が公式 UI ではなくフォーラムの Python 回避策として語られている。Movie Render Graph の目次には Per-shot settings や Shot ranges があるが、本文は取得できていない ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/movie-render-graph-in-unreal-engine))。5.6/5.7 では単一フレームのサブシーケンスにカスタムフレーム範囲を使うと二重フレームが出る報告があり ([UE フォーラム](https://forums.unrealengine.com/t/5-6-x-5-7-x-movie-render-graph-double-frames-in-outputs-custom-frame-range/2709369))、ショット単位の運用には既知の落とし穴がある。Fab のトレーラー向けプラグインはカメラ・レンズ・フレーム選択の補助が中心で、Instant Movie Maker はトレーラーマーカーからショット数・長さ・FPS を設定して Level Sequence を一括生成しバッチレンダするが、既定では既存アセットを上書きしない程度で、変更検知の記述はない ([Fab](https://www.fab.com/listings/5eac9e24-50cb-429f-a222-011196be666a))。

プロの現場の再現性も、仕組みというより運用である。Derek Lieu は「any function which can reset the game's state to what it was a few seconds or minutes ago is a HUGE time saver」と書く ([Derek Lieu](https://www.derek-lieu.com/blog/2018/5/1/the-best-debug-tools-for-game-trailer-capture))。EA は複数テイクを撮って選ぶことで再現性の問題を回避している。Saints Row: The Third は、デバッグカメラを改造した Machinima_Mode(プログラマー約2日)を外注に渡し、キャプチャ依頼が90%減ったと報告した(2012年、古い事例)([GDC Vault](https://gdcvault.com/play/1015354/Saints-Row-the-Third-Real))。「ゲーム側がカメラツールを持ち、外部に渡す」ことの価値を示す数少ない一次ソースである。

映像業界のレビュー基盤は、ショット単位のステータス、バージョン、フレーム固定の注釈を成熟した形で持つ。Kitsu はプレイリスト内でコメントと注釈を付け、クライアントが「Retake」に変更して修正を依頼できる ([Kitsu](https://kitsu.cg-wire.com/getting-started-client))。SyncSketch は注釈をフレームに固定する ([SyncSketch](https://support.syncsketch.com/hc/en-us/articles/32393818685588-Reviewing-3D-Models-and-Animations))。しかし対象は数十人規模の制作会社で、席課金と承認ワークフローは1人の開発者には過剰である。価格は出典ごとに食い違う。Flow Production Tracking は第三者掲載で約 $45/ユーザー/月だが、公式価格は取得できていない ([Software Advice](https://www.softwareadvice.com/project-management/shotgrid-profile/))。Kitsu は年払いで €20〜35/ユーザー/月 ([CGWire](https://www.cg-wire.com/pricing))、ftrack は Studio $25/Review $15 ([ftrack](https://www.ftrack.com/en/pricing))、SyncSketch は $6.80〜$12 と情報源で揺れる。上流が変わったときに承認が自動で外れるかは、どのツールでも一次情報を確認できなかった。Kitsu の承認は人がステータスを変える運用に見える(推測)。

差分レンダの仕組みで最も近いのは Houdini PDG である。ワークアイテムの状態を Clean / DirtyStale / DirtyMissing などに分け、変わった分だけ cook し直す ([SideFX](https://www.sidefx.com/docs/houdini/tops/pdg/workItemCacheState.html))。ただし TOPs は入出力ファイルの中身を確認せず、中間ファイルを手で差し替えても下流は dirty にならない ([SideFX フォーラム](https://www.sidefx.com/forum/post/316144))。AWS Deadline Cloud は一部フレームを再投入して確認してから全範囲を流せるが、入力の変更検出は記述が見つからない ([AWS](https://docs.aws.amazon.com/deadline-cloud/latest/userguide/view-a-job.html))。定義の内容ハッシュで take を管理する shotpilot の方式のほうが、手動差し替えを検出できる分だけ厳密である。

## 生成動画と汎用エージェントは別の問題を解き、最も近い競合は研究止まりである

AI 動画生成と自動編集は、編集時間、ビート同期、縦切り、ナレーションを解くが、入力は常に既存の映像か静止画で、エンジンを知らない。DaVinci Resolve 20 の AI Detect Music Beats や Premiere の Media Intelligence は音とカットの同期と検索に効く ([ProVideo Coalition](https://www.provideocoalition.com/davinci-resolve-20-released/))。ゲームトレーラー向けをうたう Invideo、Dreamina、VO3 AI は、映像アップロード型か 8秒前後の生成クリップで、エンジンから撮るものは見つからなかった ([VO3 AI](https://www.vo3ai.com/tools/ai-game-trailer-generator))。生成映像には明確な炎上の先例がある。ARK: Aquatica のトレーラーは、リードデザイナーが「マーケ部門が、我々のアセットの静止画を使って AI アニメのトレーラーを作った」と説明し、低評価率は97%に達した ([80.lv](https://80.lv/articles/ark-survival-evolved-s-ai-animated-trailer-was-created-by-the-marketing-department-said-dev))。炎上の構造は「生成映像が実際の製品と違う」ことと「開発チームが知らない」ことで、実ゲームから撮れば両方を避けられる。Steam は2026年1月の改訂で、マーケ素材で使った生成 AI の開示を求める。ただしトレーラーが明示対象かは一次で未確認である ([VGC](https://www.videogameschronicle.com/news/valve-has-significantly-rewritten-steams-rules-for-how-developers-much-disclose-ai-use))。ハイライト検出ツール(Medal、Eklipse、Outplayed)はキルや勝利のテレメトリに基づくプレイヤー向けで、開発者がトレーラーに使う証拠は見つからなかった。

エンジン内エージェントは2026年に急速に厚くなった。Epic は UE 5.7 でエディタ内 AI Assistant を追加し ([DigitalProduction](https://digitalproduction.com/2025/11/12/unreal-engine-5-7-foliage-pcg-and-in-editor-ai/))、UE 5.8(2026-06-17)で実験的な MCP サーバーを同梱した。Claude や Gemini が Blueprint、アセット、レベル、マテリアルに触れ、UE6 では MCP を中核にするという ([Engadget](https://engadget.com/2196807/epic-games-details-how-its-embracing-gen-ai-in-unreal-engine))。ただし同記事は Sequencer やシネマティクスに触れていない。OSS の ChiR24/Unreal_mcp(約1.0k stars、MIT)は `manage_sequence` で Level Sequence・Movie Render Queue・Take Recorder を扱う ([GitHub](https://github.com/ChiR24/Unreal_mcp))。したがって Sequencer を MCP で動かす道具は既にあり、道具箱の1項目として存在する。Aura(Ramen 社)は Indie $10/月、Pro $40/月、Ultimate $200/月で、Coding、Verification、Level Design、Python バッチ編集、Editor-Use のエージェントを持つ ([GamesBeat](https://gamesbeat.com/ramen-launches-aura-1-0-to-push-agentic-ai-in-game-development/))。2026年3月に Unity 向け Coplay を買収して両エンジンに対応した ([Coplay](https://coplay.dev/blog/ramen-acquires-coplay))。Aura の Sequencer・カメラ対応は検索では確認できなかった。Ludus AI は Blueprint コパイロットとコード生成が中心で、価格と対応バージョンがサイトごとに食い違う ([GetApp](https://www.getapp.com/emerging-technology-software/a/ludus-ai/))。

実機評価は、汎用エージェントの弱点を示す。Puget Systems の UE 5.8 MCP + Claude Opus 4.8 の検証では、グレーボックスは成功した一方、プレイヤー操作の変更は壊れて直らず、PCG 都市は静的メッシュの手置きで代替されたうえ聞かれるまで伝えられなかった。1リクエストは 5〜15 分以上かかり、「直した」という誤った自己申告も出た ([Puget Systems](https://www.pugetsystems.com/blog/2026/07/09/unreal-engine-mcp-hands-on-testing-ai-inside-the-editor/))。長いレイテンシ、誤った成功報告、範囲制御の弱さが共通の弱点に見える。

最も近い競合は Cutscene Agent(arXiv 2604.25318)である。UE 内の MCP サーバー経由で、ディレクターエージェントが Animation、Cinematographer、Sound Designer、Photographer(画面を見て直す)に委任し、`add_camera`、`set_active_camera`、`take_camera_screenshot` などでネイティブな Level Sequence を出す ([arXiv](https://arxiv.org/html/2604.25318v1))。Claude Opus 4.6 が主要指標でツール使用 100% を達成した一方、審判モデルによる総合点は Opus 50.2/100、GPT-5.4 42.4、Sonnet 4.6 41.7 にとどまる。審判点は保守的と著者自身が注記している。人間の承認ステップの記述も部分再レンダの明示もなく、コード公開は確認できなかった。「制作時間を約90%削減」はサードパーティブログの主張で未検証である。自動のみでは品質が足りないことを示す数字は、人間の承認の価値の根拠に使える。FilmAgent は Unity でエージェントが映画を作り、撮影エージェント同士の討論と監督の裁定を置く。人間評価15本でカメラ平均 3.53/5(GPT-4o 単独の CoT は 1.67)だった ([Hugging Face](https://huggingface.co/papers/2501.12909.md))。研究側は「Critic がレンダ結果を見て反復修正する」自己検証が主流で、shotpilot の D-22(自己検証をさせず、人間が安い段階で承認する)とは立場が逆である。研究の評価は小規模で、ショット単位の再レンダや状態管理は論点にされていない。

## 競合リスク:公式 MCP が「つなぐ」を無料にし、勝負は定義・指紋・承認に移る

最大のリスクは Epic 公式の MCP と Aura である。Epic が MCP を公式化したことで、「UE に Claude をつなぐ」だけでは見劣りする。シーケンサー操作が一般化し、Claude Code に「ティザーを作って」と頼めば、それなりのカメラワークが出る日はすぐ来る。Aura は買収と資金で拡大しており、将来 Sequencer やトレーラー機能を足す可能性がある(推測)。それでも、汎用エージェントがこの領域で「同じこと」をするには、次の三つを自分の芯にする必要がある。宣言的な正本(shots.yaml)、内容ハッシュによる stale 判定と take の再利用、画の指紋に紐づく承認である。調べた範囲では、汎用側はこれらを持たず、Puget の結果からは範囲制御と成功報告の信頼性にも課題が見える。shotpilot の「編集してよいショットの範囲をコードで強制する」「ユーザーが直すかどうかを決める」は、ここで効く。

ただし、勝てるかは別の問題である。差別化の根拠は、Epic の MCP の具体的なツール一覧、Aura の更新履歴、Fab 全体の網羅検索を確認していない状態での「見つからなかった」にすぎない。MCP の上に shots.yaml 相当のスキル(例: `quodsoler/unreal-engine-skills` の Sequencer スキル)を載せた個人プロジェクトは既にある ([claudemarketplaces](https://claudemarketplaces.com/skills/quodsoler/unreal-engine-skills/ue-sequencer-cinematics))。したがって、アイデアそのものは真似されやすく、実装の完成度と実演の説得力で勝つしかない。Unity 側は Sequences と Live Capture のサポート終了予定、Godot は固定 FPS のみで、UE5 に絞る判断と矛盾しない。

## shotpilot との差分と、借りるべき設計パターン

shotpilot の立ち位置を、調べた各群と比べると次のとおりである。エンジン標準・プラグインに対しては、Take を人が管理する世界から、定義の指紋で管理する世界へ移す。プロの運用に対しては、キャプチャ担当の頭と作業メモにあるショットごとの設定(時間帯、配置、カメラ)をマシン可読な形で持つ。レビュー基盤に対しては、承認を人手のステータスでなく画の変化に結びつける。生成系に対しては、ティザーの画をすべてゲームから撮る。汎用エージェントに対しては、範囲をコードで縛り、検証を人間の安い段階に置く。

借りる価値が高い設計は五つある。第一は Kitsu のプレイリストと Retake の語彙で、stale のショットだけ、または選んだショットだけを順に再生する確認モードとして実装できる。第二は SyncSketch のフレーム固定注釈で、D-17 のフレームと範囲の指定がそのままこれにあたり、Claude への指示に渡す。第三は PDG の細かいキャッシュ状態で、fresh / stale / out-of-sync に「欠けている」「手で差し替えられた」を加える余地がある。第四は Boords の Premiere / Resolve 向け XML と After Effects の .jsx 書き出しで、`cut` の出力を編集ソフトに渡す経路は需要がありそうだが、D-02 の範囲を超えないよう、片方向の書き出しに限るのが安全である。第五は Saints Row の教訓で、カメラ・時間帯・NPC をゲーム側から操作できる仕組みを shots.yaml の語彙に取り込むことである。過剰なのは、席と権限、スケジュール、DRM と透かし、同期ライブレビュー、複数部門のタスク割り当て、クラウドストレージで、いずれも1人の開発者には要らない。

## 計画への示唆:次に作るもの、やらないもの、デモで言えること

次に作るべきものは三つある。一つ目は、デモの核である「敵のテクスチャを変えると、該当ショットだけ stale になり再レンダされ、他は reused のまま残る」場面の磨き込みである。前回の調査で見つかった実体験の引用「I also had to reshoot the whole thing because I decided to change my enemy textures」をそのまま再現するのがよい。二つ目は、MRQ の落とし穴への対処をテストで固定することで、ウォームアップ(カメラのカット時の挙動、枚数)をショットごとに明示し、二重フレームや最初のショット以外が出ない事象で fingerprint が壊れないようにする。三つ目は、提出前に Epic 公式 MCP のツール一覧と Aura の更新履歴を直接確認することである。これで「他にない」という主張の根拠が固まる。

やらないものも明確である。録画後の自由編集(D-02)、席課金や権限管理のような制作会社向けの管理機能、生成映像でティザーの画を作ること(D-23、D-33)、Unity・Godot への展開(D-11)、Claude に自己検証させること(D-22)は引き続き見送る。研究側の Critic 方式を取り入れたくなる誘惑があるが、自動のみの総合点が 50/100 程度という Cutscene Agent の数字は、自動で磨くより人間が1カットずつ承認する価値を支える。ただし、D-22 を貫く理由は「研究が間違っている」ではなく、「Puget の検証が示す誤った成功報告を避け、検証を人間の安い段階に置く」設計判断として説明するのが誠実である。

デモで言えることは、次のとおりである。ゲームが変わるたびに全部撮り直す痛みは複数の開発者が書いている。ティザーの画はすべてゲームから撮る。直したショットだけが撮り直される。承認は画が変わると外れる。範囲外のショットは Claude が変更できない(コードで強制)。言えないことは、「他に同種の製品は存在しない」「開発者が部分再レンダを求めている」「Epic 公式 MCP や Aura では不可能」「時間を90%削減する」の四つである。いずれも一次の裏付けがないか、不在の証明になってしまう。生成 AI を使わないことは強みだが、Steam の AI 開示規則がトレーラーに及ぶかは未確認なので、その点に踏み込む場合は Steamworks の最新文言を確認してから言う。

## 証拠の弱いところ

この調査の確度は均一ではない。公式ドキュメントを本文まで取得できなかったものは、Sequencer 概要、Movie Render Graph の各小節、Flow Production Tracking のステータスと注釈の仕様、Frame.io V4 の承認仕様、Epic 公式の UE 5.8 MCP ツール一覧、Fab の個別リスティング、LTX Studio 公式、Autodesk の機能ページである。多くは検索結果の要約経由で、原文照合をしていない。価格は、Flow Production Tracking(公式未取得で約 $45 はサードパーティ)、SyncSketch、ftrack の Review、Katalist、Ludus AI、Medal、Outplayed で出典間の食い違いがある。FrameForge、Shot Designer、StudioBinder の価格は 2011〜2015 年など古い情報を含む。未確認の製品・主張は、Sora の提供終了の記事、NVIDIA Ansel と Highlights、Flop Agent の機能と買収の一次ソース、依頼文にあった CineMPC(検索で見つからず実在未確認)、FilmFlow の定量結果(要約サイト経由)である。日本語の PV 制作会社の工程、Ant Workshop や Mammoth などのキャプチャ会社の工程と料金も見つからなかった。ファーム側では Tractor、旧版 Deadline、Nuke のキャッシュ、USD のバージョニングは調べておらず、「ファームは変更検出を持たない」は Deadline Cloud の記述に限った話である。

## Conclusion

調査前の想定では、競合は「AI でトレーラーを作る」製品群だと思われた。実際には、似たものは三層に分かれて存在していた。エンジンが「撮る」を支え、映像業界が「見て承認する」を支え、汎用エージェントが「エディタを動かす」を支える。そして三層のあいだにある「何が古いかを判定し、その分だけ撮り、承認を画に結びつける」継ぎ目だけが空いている。shotpilot の価値は AI の賢さではなく、この継ぎ目を shots.yaml と fingerprint で埋めた点にある。汎用エージェントが賢くなるほど、この継ぎ目の価値は下がらず、むしろ「どのエージェントが書いても、変わったショットだけ撮り直す」土台として上がる。

ただし、この空白は網羅調査で確かめたものではなく、Epic と Aura の次の一手で閉じうる。したがって提出前の優先順位は、機能追加より、公式 MCP と Aura の実機確認、デモの再現性、言える範囲と言えない範囲の線引きである。
